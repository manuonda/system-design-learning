## 1. Overview

The Singleton pattern is a **creational** pattern, but unlike the others in that category, it isn't about *how* to create objects — it's about **how many instances** get created.

## 2. The Problem: Why We Need a Singleton

Domain model:
- `Task`: `id`, `name`, `status` (`TaskStatus` enum: `TO_DO`, `IN_PROGRESS`, `ON_HOLD`, `DONE`)
- `InMemoryTaskRepository`: stores tasks in a `HashMap<Long, Task>`

`InMemoryTaskRepository` has a **public constructor** — nothing stops multiple instances from being created, and each one keeps its own independent `HashMap`. A task saved through one instance is completely invisible to another:

```java
@Test
void givenMultipleRepositoryInstances_whenSavingToOne_thenOtherCannotFind() {
    InMemoryTaskRepository repoA = new InMemoryTaskRepository();
    InMemoryTaskRepository repoB = new InMemoryTaskRepository();

    repoA.save(1L, new Task(1L, "Write tests", TaskStatus.TO_DO));

    assertNull(repoB.findById(1L));
}
```

In a real application, this kind of fragmentation can cause data loss and inconsistent, hard-to-debug behavior. For a stateful resource like an in-memory store, we need the guarantee that **every part of the application works with the same instance**. That's exactly what Singleton provides.

## 3. The Singleton Pattern

> A creational pattern that guarantees a class has exactly one instance and provides a global access point to it.

Two mechanisms make it work:
1. The constructor is **private**, so no external code can call `new` on the class.
2. A static method (usually `getInstance()`) **returns the single instance**, creating it if necessary.

This gives centralized control over instantiation — any part of the application that needs the singleton calls `getInstance()` and gets back the same object every time.

## 4. Implementation

We'll build through three approaches, from simplest to most robust.

### 4.1. Eager Initialization

The instance is created when the class loads:

```java
public class InMemoryTaskRepositorySingleton {

    private static final InMemoryTaskRepositorySingleton INSTANCE = new InMemoryTaskRepositorySingleton();

    private InMemoryTaskRepositorySingleton() {
    }

    public static InMemoryTaskRepositorySingleton getInstance() {
        return INSTANCE;
    }

    // same methods as InMemoryTaskRepository
}
```

`INSTANCE` is initialized directly in its declaration. The JVM guarantees static fields are initialized exactly once when the class loads, which makes this approach **inherently thread-safe with no synchronization code**.

Trade-off: the instance is created whether or not it's ever used. Fine for lightweight objects like this repository; potentially wasteful for expensive resources (large memory allocations, external connections). In most practical cases, though, eager initialization is a solid default.

```java
@Test
void givenSingletonRepository_whenGetInstanceCalledTwice_thenSameInstance() {
    InMemoryTaskRepositorySingleton first = InMemoryTaskRepositorySingleton.getInstance();
    InMemoryTaskRepositorySingleton second = InMemoryTaskRepositorySingleton.getInstance();

    assertSame(first, second);

    first.save(1L, new Task(1L, "Deploy release", TaskStatus.TO_DO));

    assertEquals("Deploy release", second.findById(1L).getName());
}
```

`assertSame()` checks reference equality. Saving through `first` and reading through `second` proves it's a single shared `HashMap` — the core guarantee of the pattern.

### 4.2. Double-Checked Locking

To delay creation until actually requested, we need **lazy initialization**. A naive null-check-then-create breaks in a multithreaded environment — two threads could both see `null` and each create a separate instance, defeating the purpose.

**Double-Checked Locking (DCL)** fixes this:

```java
public class InMemoryTaskRepositorySingletonDCL {

    private static volatile InMemoryTaskRepositorySingletonDCL instance;

    private final Map<Long, Task> store = new HashMap<>();

    private InMemoryTaskRepositorySingletonDCL() {
    }

    public static InMemoryTaskRepositorySingletonDCL getInstance() {
        if (instance == null) {
            synchronized (InMemoryTaskRepositorySingletonDCL.class) {
                if (instance == null) {
                    instance = new InMemoryTaskRepositorySingletonDCL();
                }
            }
        }
        return instance;
    }
}
```

Mechanics:
- The **first null check** avoids synchronization overhead on every call.
- The **synchronized block** ensures only one thread enters the creation logic at a time.
- The **second null check** handles the race where another thread created the instance between the first check and acquiring the lock.
- **`volatile`** prevents instruction reordering that could expose a partially constructed object to other threads.

Thread-safe and lazy, but noticeably more complex than eager initialization. The `volatile` keyword and double null check are easy to get wrong, and the performance benefit over eager initialization is rarely meaningful in practice. Public API is identical (`getInstance()`), so the same test logic applies — only the internal initialization strategy changed.

### 4.3. Enum Singleton

The **recommended approach in modern Java**, though it doesn't fit every situation — enums can't extend classes. Demonstrated here with `TaskIdGenerator`, a simple counter for unique sequential task IDs:

```java
public enum TaskIdGenerator {

    INSTANCE;

    private long currentId = 0;

    public long nextId() {
        return ++currentId;
    }
}
```

Used as `TaskIdGenerator.INSTANCE.nextId()`. All the singleton machinery disappears: the JVM handles thread-safe instantiation, serialization, and reflection protection automatically. No private constructor to write, no `getInstance()` to maintain, and no risk of accidental multiple instances — even attempts via reflection or deserialization are blocked by the JVM's enum guarantees.

Limitation: enum singletons **can't extend a class** because enums implicitly extend `java.lang.Enum`. Use eager initialization when inheritance is required; prefer Enum when it isn't.

```java
@Test
void givenEnumSingleton_whenAccessedTwice_thenSameInstanceAndConsecutiveIds() {
    TaskIdGenerator first = TaskIdGenerator.INSTANCE;
    TaskIdGenerator second = TaskIdGenerator.INSTANCE;

    assertSame(first, second);

    long id1 = first.nextId();
    long id2 = second.nextId();

    assertEquals(id1 + 1, id2);
}
```

Both references point to the same enum constant (`assertSame()` passes); the consecutive IDs confirm shared state — `nextId()` through either reference increments the same counter.

## 5. When to Use / When Not to Use

### 5.1. Good Use Cases

Shared stateful resources where multiple instances would cause inconsistency or waste: in-memory caches, connection pools, configuration holders, ID generators. Logging frameworks and registries are natural fits too — the whole application needs one entry point. Also appropriate for system-level constraints (e.g., an object representing the JVM runtime environment), where multiple instances would waste resources or cause state inconsistency.

### 5.2. When to Avoid

- **Stateless classes** — no shared state to protect, so a singleton just adds unnecessary coupling. Instantiate wherever needed instead.
- **Hidden dependencies** — a class calling `SomeService.getInstance()` internally hides that dependency from its constructor/method signature, making the code harder to reason about and change.
- When a **DI framework** (like Spring) is available, it manages instance lifecycles more flexibly than the classic Singleton pattern, without these drawbacks.

### 5.3. The Testing Challenge

Since a singleton's state persists for the class's lifetime, it also persists **between test methods**. A `clear()` method is a common workaround:

```java
public void clear() {
    store.clear();
}
```

```java
@BeforeEach
void setUp() {
    InMemoryTaskRepositorySingleton.getInstance().clear();
}
```

```java
@Test
void givenClearedRepository_whenFindById_thenReturnsNull() {
    InMemoryTaskRepositorySingleton repo = InMemoryTaskRepositorySingleton.getInstance();

    assertNull(repo.findById(1L));
}
```

Without `clear()` in `@BeforeEach`, this test would fail if run after the earlier one — the "Deploy release" task would still be sitting in the `HashMap`. Note `clear()` is a **design compromise**: it exists purely for testing and wouldn't otherwise belong on the class. This test-isolation difficulty is one of the key reasons the classic Singleton is sometimes called an anti-pattern.

## 6. Real-World Singleton Usage

### 6.1. `Runtime.getRuntime()` in the JDK

`java.lang.Runtime` is a classic JDK Singleton — one JVM, one `Runtime` instance, accessed via `Runtime.getRuntime()`. It exposes the runtime environment: available processors, memory info, the ability to execute external processes.

Implemented with eager initialization, created when the class loads. Multiple `Runtime` instances wouldn't make sense — there's only one set of memory counters, one process table, one set of available processors. A textbook example of the pattern.

### 6.2. Spring's Singleton Scope

Spring beans are singletons by default, but this is **not the same as the GoF Singleton pattern** — an important distinction.

| | GoF Singleton | Spring singleton scope |
|---|---|---|
| Guarantee | One instance, globally, enforced by the class itself | One instance per IoC container, managed by the framework |
| Mechanism | Private constructor + static `getInstance()` | Plain class, no special constructor/method |
| Who enforces it | The class | Spring instantiates it once and reuses it |

This framework-managed approach avoids most classic Singleton drawbacks: beans are easy to test (instantiate normally in tests), dependencies aren't hidden (injected explicitly), and lifecycle is managed externally rather than hardcoded into the class.

In modern Java applications, letting the framework manage the singleton lifecycle is generally preferred over hardcoding it into the class.

## 7. Conclusion

| Approach | Lazy? | Thread-safe? | Complexity | Can extend a class? |
|---|---|---|---|---|
| Eager initialization | No | Yes (JVM guarantee) | Low | Yes |
| Double-Checked Locking | Yes | Yes (with `volatile`) | High | Yes |
| Enum Singleton | No | Yes (JVM guarantee) | Lowest | No |

Singleton solves real problems around shared-state consistency, but carries real downsides: test isolation needs workarounds, dependencies get hidden, and the class takes on lifecycle-management responsibility. In applications using dependency injection, framework-managed singletons are the preferred approach — same single-instance guarantee, none of the classic drawbacks.
