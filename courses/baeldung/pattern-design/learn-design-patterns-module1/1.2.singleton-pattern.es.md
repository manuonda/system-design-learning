## 1. Descripción general

El patrón Singleton es un patrón **creacional**, pero a diferencia de los demás de esa categoría, no trata sobre *cómo* crear objetos, sino sobre **cuántas instancias** se crean.

Módulos:
- Inicio: `the-singleton-pattern-start`
- Fin (solución de referencia): `the-singleton-pattern-end`

## 2. El problema: por qué necesitamos un Singleton

Modelo de dominio:
- `Task`: `id`, `name`, `status` (enum `TaskStatus`: `TO_DO`, `IN_PROGRESS`, `ON_HOLD`, `DONE`)
- `InMemoryTaskRepository`: almacena tareas en un `HashMap<Long, Task>`

`InMemoryTaskRepository` tiene un **constructor público** — nada impide crear múltiples instancias, y cada una mantiene su propio `HashMap` independiente. Una tarea guardada a través de una instancia es completamente invisible para otra:

```java
@Test
void givenMultipleRepositoryInstances_whenSavingToOne_thenOtherCannotFind() {
    InMemoryTaskRepository repoA = new InMemoryTaskRepository();
    InMemoryTaskRepository repoB = new InMemoryTaskRepository();

    repoA.save(1L, new Task(1L, "Write tests", TaskStatus.TO_DO));

    assertNull(repoB.findById(1L));
}
```

En una aplicación real, este tipo de fragmentación puede causar pérdida de datos y comportamiento inconsistente difícil de depurar. Para un recurso con estado como un almacén en memoria, necesitamos la garantía de que **cada parte de la aplicación trabaje con la misma instancia**. Eso es exactamente lo que ofrece Singleton.

## 3. El patrón Singleton

> Un patrón creacional que garantiza que una clase tenga exactamente una instancia y proporciona un punto de acceso global a ella.

Dos mecanismos lo hacen posible:
1. El constructor es **privado**, de modo que ningún código externo puede llamar a `new` sobre la clase.
2. Un método estático (normalmente `getInstance()`) **devuelve la única instancia**, creándola si es necesario.

Esto da control centralizado sobre la instanciación — cualquier parte de la aplicación que necesite el singleton llama a `getInstance()` y recibe siempre el mismo objeto.

## 4. Implementación

Construiremos tres enfoques, del más simple al más robusto.

### 4.1. Inicialización inmediata (Eager)

La instancia se crea al cargar la clase:

```java
public class InMemoryTaskRepositorySingleton {

    private static final InMemoryTaskRepositorySingleton INSTANCE = new InMemoryTaskRepositorySingleton();

    private InMemoryTaskRepositorySingleton() {
    }

    public static InMemoryTaskRepositorySingleton getInstance() {
        return INSTANCE;
    }

    // mismos métodos que InMemoryTaskRepository
}
```

`INSTANCE` se inicializa directamente en su declaración. La JVM garantiza que los campos estáticos se inicializan exactamente una vez al cargar la clase, lo que hace este enfoque **intrínsecamente seguro para hilos, sin código de sincronización**.

Contrapartida: la instancia se crea se use o no. Está bien para objetos ligeros como este repositorio; puede ser un desperdicio para recursos costosos (grandes asignaciones de memoria, conexiones externas). Aun así, en la mayoría de los casos prácticos, la inicialización inmediata es una buena opción por defecto.

```java
@Test
void givenSingletonRepository_whenGetInstanceCalledTwice_thenSameInstance() {
    InMemoryTaskRepositorySingleton first = InMemoryTaskRepositorySingleton.getInstance();
    InMemoryTaskRepositorySingleton second = InMemoryTaskRepositorySingleton.getInstance();

    assertSame(first, second);

    first.save(1L, new Task(1L, "Deploy release", TaskStatus.TO_DO));

    assertEquals("Deploy release", second.findById(1L).getName());
}
```

`assertSame()` comprueba igualdad de referencia. Guardar a través de `first` y leer a través de `second` prueba que es un único `HashMap` compartido — la garantía central del patrón.

### 4.2. Double-Checked Locking

Para retrasar la creación hasta que realmente se solicite, necesitamos **inicialización perezosa (lazy)**. Una comprobación ingenua de `null` seguida de creación falla en un entorno multihilo — dos hilos podrían ver ambos `null` y cada uno crear su propia instancia, arruinando el propósito.

**Double-Checked Locking (DCL)** soluciona esto:

```java
public class InMemoryTaskRepositorySingletonDCL {

    private static volatile InMemoryTaskRepositorySingletonDCL instance;

    private final Map<Long, Task> store = new HashMap<>();

    private InMemoryTaskRepositorySingletonDCL() {
    }

    public static InMemoryTaskRepositorySingletonDCL getInstance() {
        if (instance == null) {
            synchronized (InMemoryTaskRepositorySingletonDCL.class) {
                if (instance == null) {
                    instance = new InMemoryTaskRepositorySingletonDCL();
                }
            }
        }
        return instance;
    }
}
```

Mecánica:
- La **primera comprobación de `null`** evita el costo de sincronización en cada llamada.
- El **bloque `synchronized`** asegura que solo un hilo entre a la lógica de creación a la vez.
- La **segunda comprobación de `null`** maneja la condición de carrera en la que otro hilo creó la instancia entre la primera comprobación y la adquisición del lock.
- **`volatile`** evita el reordenamiento de instrucciones que podría exponer un objeto parcialmente construido a otros hilos.

Es seguro para hilos y perezoso, pero notablemente más complejo que la inicialización inmediata. La palabra clave `volatile` y la doble comprobación de `null` son fáciles de implementar mal, y el beneficio de rendimiento frente a la inicialización inmediata rara vez es significativo en la práctica. La API pública es idéntica (`getInstance()`), así que la misma lógica de prueba aplica — solo cambió la estrategia interna de inicialización.

### 4.3. Enum Singleton

El **enfoque recomendado en el Java moderno**, aunque no encaja en todas las situaciones — los enums no pueden extender clases. Se demuestra aquí con `TaskIdGenerator`, un contador simple para generar IDs de tarea secuenciales únicos:

```java
public enum TaskIdGenerator {

    INSTANCE;

    private long currentId = 0;

    public long nextId() {
        return ++currentId;
    }
}
```

Se usa como `TaskIdGenerator.INSTANCE.nextId()`. Toda la maquinaria del singleton desaparece: la JVM gestiona automáticamente la instanciación segura para hilos, la serialización y la protección contra reflexión. No hay constructor privado que escribir, no hay `getInstance()` que mantener, y no hay riesgo de instancias múltiples accidentales — incluso los intentos vía reflexión o deserialización son bloqueados por las garantías de enum de la JVM.

Limitación: los enum singletons **no pueden extender una clase** porque los enums extienden implícitamente `java.lang.Enum`. Usa inicialización inmediata cuando se necesite herencia; prefiere Enum cuando no.

```java
@Test
void givenEnumSingleton_whenAccessedTwice_thenSameInstanceAndConsecutiveIds() {
    TaskIdGenerator first = TaskIdGenerator.INSTANCE;
    TaskIdGenerator second = TaskIdGenerator.INSTANCE;

    assertSame(first, second);

    long id1 = first.nextId();
    long id2 = second.nextId();

    assertEquals(id1 + 1, id2);
}
```

Ambas referencias apuntan a la misma constante de enum (`assertSame()` pasa); los IDs consecutivos confirman el estado compartido — llamar a `nextId()` por cualquiera de las dos referencias incrementa el mismo contador.

## 5. Cuándo usarlo / cuándo no

### 5.1. Buenos casos de uso

Recursos con estado compartido donde múltiples instancias causarían inconsistencia o desperdicio: cachés en memoria, pools de conexiones, contenedores de configuración, generadores de ID. Los frameworks de logging y los registros también encajan naturalmente — toda la aplicación necesita un único punto de entrada. También es apropiado para restricciones a nivel de sistema (p. ej., un objeto que representa el entorno de ejecución de la JVM), donde múltiples instancias desperdiciarían recursos o causarían inconsistencia de estado.

### 5.2. Cuándo evitarlo

- **Clases sin estado** — no hay estado compartido que proteger, así que un singleton solo añade acoplamiento innecesario. Basta con instanciar donde se necesite.
- **Dependencias ocultas** — una clase que llama internamente a `SomeService.getInstance()` oculta esa dependencia de su constructor/firma de método, haciendo el código más difícil de razonar y de cambiar.
- Cuando hay disponible un **framework de inyección de dependencias** (como Spring), este gestiona el ciclo de vida de las instancias de forma más flexible que el patrón Singleton clásico, sin estos inconvenientes.

### 5.3. El desafío de las pruebas

Como el estado de un singleton persiste durante toda la vida de la clase, también persiste **entre métodos de prueba**. Un método `clear()` es una solución común:

```java
public void clear() {
    store.clear();
}
```

```java
@BeforeEach
void setUp() {
    InMemoryTaskRepositorySingleton.getInstance().clear();
}
```

```java
@Test
void givenClearedRepository_whenFindById_thenReturnsNull() {
    InMemoryTaskRepositorySingleton repo = InMemoryTaskRepositorySingleton.getInstance();

    assertNull(repo.findById(1L));
}
```

Sin `clear()` en `@BeforeEach`, esta prueba fallaría si se ejecuta después de la anterior — la tarea "Deploy release" seguiría en el `HashMap`. Nótese que `clear()` es un **compromiso de diseño**: existe únicamente para fines de prueba y de otro modo no pertenecería a la clase. Esta dificultad de aislamiento de pruebas es una de las razones clave por las que el Singleton clásico a veces se considera un anti-patrón.

## 6. Uso de Singleton en el mundo real

### 6.1. `Runtime.getRuntime()` en el JDK

`java.lang.Runtime` es un Singleton clásico del JDK — hay una JVM, así que hay una instancia de `Runtime`, accedida vía `Runtime.getRuntime()`. Da acceso al entorno de ejecución: procesadores disponibles, información de memoria, capacidad de ejecutar procesos externos.

Implementado con inicialización inmediata, creado al cargar la clase. Tener múltiples instancias de `Runtime` no tendría sentido — solo hay un conjunto de contadores de memoria, una tabla de procesos y un conjunto de procesadores disponibles. Un ejemplo de manual del patrón.

### 6.2. El alcance Singleton de Spring

Los beans de Spring son singletons por defecto, pero esto **no es lo mismo que el patrón Singleton de GoF** — una distinción importante.

| | Singleton GoF | Alcance singleton de Spring |
|---|---|---|
| Garantía | Una instancia, globalmente, impuesta por la propia clase | Una instancia por contenedor IoC, gestionada por el framework |
| Mecanismo | Constructor privado + `getInstance()` estático | Clase normal, sin constructor/método especial |
| Quién lo impone | La clase | Spring la instancia una vez y la reutiliza |

Este enfoque gestionado por el framework evita la mayoría de los inconvenientes clásicos del Singleton: los beans son fáciles de probar (se instancian normalmente en las pruebas), las dependencias no están ocultas (se inyectan explícitamente), y el ciclo de vida se gestiona externamente en lugar de estar codificado en la clase.

En las aplicaciones Java modernas, generalmente se prefiere que el framework gestione el ciclo de vida del singleton en lugar de codificarlo en la propia clase.

## 7. Conclusión

| Enfoque | ¿Perezoso? | ¿Seguro para hilos? | Complejidad | ¿Puede extender una clase? |
|---|---|---|---|---|
| Inicialización inmediata | No | Sí (garantía de la JVM) | Baja | Sí |
| Double-Checked Locking | Sí | Sí (con `volatile`) | Alta | Sí |
| Enum Singleton | No | Sí (garantía de la JVM) | La más baja | No |

Singleton resuelve problemas reales relacionados con la consistencia del estado compartido, pero conlleva desventajas reales: el aislamiento de pruebas requiere soluciones alternativas, las dependencias quedan ocultas, y la clase asume la responsabilidad de gestionar su propio ciclo de vida. En aplicaciones que usan inyección de dependencias, los singletons gestionados por el framework son el enfoque preferido — misma garantía de instancia única, sin los inconvenientes clásicos.
