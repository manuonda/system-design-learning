# Aprende Patrones de Diseño — Módulo 1, Lección 3: El Patrón Builder

## 1. Descripción general

Builder es un patrón **creacional** que resuelve un problema muy práctico: construir objetos con muchos campos, algunos de ellos opcionales.

Módulos:
- Inicio: `the-builder-pattern-start`
- Fin (solución de referencia): `the-builder-pattern-end`

## 2. El problema: constructores telescópicos

`Task` tiene nueve campos: `id` (`Long`), `name` (`String`), `description` (`String`), `dueDate` (`LocalDate`), `status` (`TaskStatus`), `priority` (`Priority`), `assignee` (`String`), `project` (`String`), `estimatedHours` (`Double`).
`TaskStatus`: `TO_DO`, `IN_PROGRESS`, `ON_HOLD`, `DONE`. `Priority`: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.

Para admitir la creación de una tarea con distintas combinaciones de campos opcionales, necesitaríamos múltiples sobrecargas de constructor — `Task(name)`, `Task(name, description)`, `Task(name, description, dueDate)`, y así hasta un constructor completo de nueve parámetros. Este es el **antipatrón del constructor telescópico**, y crea dos problemas concretos.

**1. El punto de llamada es difícil de leer:**

```java
Task task = new Task(null, "Design login page",
        "Create wireframes and implement the login UI with OAuth support",
        LocalDate.of(2050, 6, 1), TaskStatus.TO_DO, Priority.HIGH,
        "Alice", "Website Redesign", 12.0);
```

Con nueve parámetros posicionales, es muy difícil saber qué argumento corresponde a qué campo. ¿`"Alice"` es el assignee o el project? ¿`12.0` son las horas estimadas o algo más? Pasar `null` para el ID resulta incómodo, y si intercambiamos `"Alice"` por `"Website Redesign"` el código compila sin problemas porque ambos son strings — el compilador no puede detectar ese error.

**2. Cada nuevo campo opcional implica otra sobrecarga de constructor.** El número de constructores crece rápidamente y se vuelve inmanejable.

Builder resuelve ambos problemas reemplazando los constructores posicionales por **métodos con nombre**.

## 3. ¿Qué es el patrón Builder?

> Un patrón creacional que separa la construcción de un objeto complejo de su representación.

Mientras que Singleton controla *cuántas* instancias de una clase existen, Builder controla *cómo* se construye una instancia.

### 3.1. Cómo resuelve el problema

En lugar de pasar una larga lista de argumentos posicionales a un constructor, configuramos el objeto paso a paso y producimos el resultado final cuando estamos listos. Desde el punto de vista de quien llama: cada parámetro tiene **nombre**, el orden no importa, y los campos opcionales simplemente pueden omitirse — el punto de llamada se vuelve autodescriptivo.

En esta implementación, `Task` también es **inmutable**: una vez construido, no puede cambiar. Es un emparejamiento natural — el Builder gestiona la construcción paso a paso, y el `Task` terminado bloquea su estado. Agregar un nuevo campo opcional más adelante no rompe el código existente; quienes no lo necesiten simplemente no llaman al nuevo método.

### 3.2. Elementos clave

| Elemento | Rol |
|---|---|
| **Builder** | Objeto separado que refleja los campos del producto |
| Setters fluidos | Acumulan configuración, cada uno devuelve `this` para encadenar |
| `build()` | Toma el estado acumulado y produce el objeto final |

## 4. Implementación

### 4.1. Actualizar la clase `Task`

El constructor se vuelve **privado**, acepta un `Builder` y copia sus campos; cada campo se vuelve **final**:

```java
public class Task {

    private final Long id;
    private final String name;
    private final String description;
    private final LocalDate dueDate;
    private final TaskStatus status;
    private final Priority priority;
    private final String assignee;
    private final String project;
    private final Double estimatedHours;

    private Task(Builder builder) {
        this.id = builder.id;
        this.name = builder.name;
        this.description = builder.description;
        this.dueDate = builder.dueDate;
        this.status = builder.status;
        this.priority = builder.priority;
        this.assignee = builder.assignee;
        this.project = builder.project;
        this.estimatedHours = builder.estimatedHours;
    }

    // getters estándar
}
```

Comparado con el proyecto inicial: se eliminan todos los setters, cada campo es `final`. Esto **no es equivalente** al `Task` mutable original con métodos setter que podían cambiar cualquier campo tras la construcción — el nuevo `Task` congela sus datos en el momento de la construcción. El constructor privado obliga a pasar por el `Builder`, y una vez construido, un `Task` no puede modificarse.

### 4.2. Creación del Builder

Una clase interna estática que refleja los mismos nueve campos, cada uno con un setter fluido:

```java
public static class Builder {

    private Long id;
    private final String name;
    private String description;
    private LocalDate dueDate;
    private TaskStatus status = TaskStatus.TO_DO;
    private Priority priority = Priority.MEDIUM;
    private String assignee;
    private String project;
    private Double estimatedHours;

    public Builder(String name) {
        this.name = name;
    }

    public Builder id(Long id) {
        this.id = id;
        return this;
    }

    public Builder description(String description) {
        this.description = description;
        return this;
    }

    public Builder dueDate(LocalDate dueDate) {
        this.dueDate = dueDate;
        return this;
    }

    public Builder status(TaskStatus status) {
        this.status = status;
        return this;
    }

    public Builder priority(Priority priority) {
        this.priority = priority;
        return this;
    }

    public Builder assignee(String assignee) {
        this.assignee = assignee;
        return this;
    }

    public Builder project(String project) {
        this.project = project;
        return this;
    }

    public Builder estimatedHours(Double estimatedHours) {
        this.estimatedHours = estimatedHours;
        return this;
    }

    public Task build() {
        return new Task(this);
    }
}
```

`name` es el único parámetro obligatorio, aceptado en el propio constructor del `Builder` — esto garantiza que todo `Task` tenga al menos un nombre. `status` por defecto es `TaskStatus.TO_DO`, `priority` por defecto es `Priority.MEDIUM`; el resto de campos opcionales por defecto es `null`.

Cada método fluido establece un campo y devuelve `this` (encadenamiento de métodos). `build()` crea un nuevo `Task` pasando el propio `Builder` al constructor privado.

> **Nota de convención:** una clase interna estática `Builder` es una convención muy adoptada en el Java moderno, popularizada por *Effective Java*. Se ubica junto a su clase producto y puede acceder al constructor privado. (También podría ser una clase de nivel superior separada, aunque el estilo de clase interna es mucho más común.)

### 4.3. Pruebas

```java
class BuilderPatternUnitTest {

    @Test
    void givenAllFieldsSet_whenBuild_thenTaskHasAllValues() {
        Task task = new Task.Builder("Design login page")
                .id(1L)
                .description("Create wireframes and implement the login UI with OAuth support")
                .dueDate(LocalDate.of(2050, 6, 1))
                .status(TaskStatus.IN_PROGRESS)
                .priority(Priority.HIGH)
                .assignee("Alice")
                .project("Website Redesign")
                .estimatedHours(12.0)
                .build();

        assertEquals("Design login page", task.getName());
        assertEquals(1L, task.getId());
        assertEquals("Create wireframes and implement the login UI with OAuth support", task.getDescription());
        assertEquals(LocalDate.of(2050, 6, 1), task.getDueDate());
        assertEquals(TaskStatus.IN_PROGRESS, task.getStatus());
        assertEquals(Priority.HIGH, task.getPriority());
        assertEquals("Alice", task.getAssignee());
        assertEquals("Website Redesign", task.getProject());
        assertEquals(12.0, task.getEstimatedHours());
    }

    @Test
    void givenOnlyRequiredField_whenBuild_thenDefaultsApplied() {
        Task task = new Task.Builder("Quick task").build();

        assertEquals("Quick task", task.getName());
        assertEquals(TaskStatus.TO_DO, task.getStatus());
        assertEquals(Priority.MEDIUM, task.getPriority());
        assertNull(task.getId());
        assertNull(task.getDescription());
        assertNull(task.getDueDate());
        assertNull(task.getAssignee());
        assertNull(task.getProject());
        assertNull(task.getEstimatedHours());
    }
}
```

Compara la llamada al builder con el constructor telescópico de la Sección 2: cada parámetro tiene nombre, el orden es irrelevante, y los campos opcionales simplemente se omiten. La segunda prueba confirma que los valores por defecto (`TO_DO`, `MEDIUM`) se aplican cuando solo se establece el `name` obligatorio, y que cada campo opcional no especificado es `null`.

> En código de producción, `build()` también podría validar campos requeridos (p. ej., lanzar `IllegalStateException` si `name` es `null`) — se mantiene simple aquí.

Ejecutar: `mvn test`.

## 5. Cuándo usarlo / cuándo no

### 5.1. Úsalo cuando
- Una clase tiene **cuatro o más campos**, muchos de ellos opcionales — aquí es donde el problema del constructor telescópico se vuelve real.
- La construcción implica **lógica compleja**: múltiples pasos, valores por defecto condicionales, o validación que el Builder puede encapsular detrás de una API limpia.
- El punto de llamada debería ser **autodescriptivo** — los métodos con nombre hacen explícita la intención de cada parámetro.

### 5.2. Evítalo cuando
- Una clase tiene solo **dos o tres campos** — un constructor directo es más claro y conciso; el Builder añade boilerplate sin beneficio real.
- **Todos los campos son obligatorios**, sin parámetros opcionales — un constructor comunica esa restricción de forma más directa. En el Java moderno, un **record** puede encajar aún mejor en estos casos.
- Cada llamada a `build()` asigna un objeto `Builder` extra — despreciable en la gran mayoría de los casos; solo importa en bucles internos extremadamente exigentes que crean millones de objetos, algo raramente relevante en la práctica.

### 5.3. La contrapartida de la verbosidad

El principal inconveniente es el **boilerplate** — la clase `Builder` duplica cada campo de la clase producto. Para un `Task` de nueve campos, el `Builder` también tiene nueve campos, nueve setters y un método `build()`: duplicación real que crece linealmente con el número de campos.

Es una contrapartida honesta: verbosidad en la definición de la clase, a cambio de legibilidad en el punto de llamada. Suele valer la pena para clases con muchos parámetros opcionales. Los IDEs modernos pueden generar gran parte de este boilerplate automáticamente, y bibliotecas como **Lombok** generan el `Builder` completo con una sola anotación `@Builder` — aquí se implementa manualmente para entender la mecánica.

## 6. Ejemplos reales de Builder (JDK)

### 6.1. `StringBuilder`

Probablemente el Builder más familiar en Java — acumula datos de caracteres mediante encadenamiento y produce el `String` final vía `toString()`:

```java
String result = new StringBuilder()
        .append("Task: ")
        .append("Design login page")
        .append(" [")
        .append("IN_PROGRESS")
        .append("]")
        .toString();
```

Mismo patrón implementado arriba: construir paso a paso, producir el resultado al final.

### 6.2. `HttpRequest.newBuilder()` (Java 11+)

Una API Builder moderna y fluida:

```java
HttpRequest request = HttpRequest.newBuilder(URI.create("https://api.example.com/tasks"))
        .header("Accept", "application/json")
        .GET()
        .build();
```

El método de fábrica estático `newBuilder()` crea el Builder, los setters fluidos configuran la petición, `build()` produce un `HttpRequest` inmutable — una aplicación de manual del estilo Builder interno estático a nivel del JDK.

### 6.3. `Calendar.Builder` (Java 8+)

Reemplaza el enfoque propenso a errores `Calendar.set(field, value)`:

```java
Calendar calendar = new Calendar.Builder()
        .setDate(2050, Calendar.JUNE, 15)
        .setTimeZone(TimeZone.getDefault())
        .build();
```

El Builder impone combinaciones válidas y produce el `Calendar` final en un solo paso, evitando el estado parcialmente construido que permitía la antigua API basada en setters (un `Calendar` podía existir con algunos campos establecidos y otros en un valor por defecto inconsistente).

## 7. Conclusión

Builder separa la construcción de un objeto de su representación, reemplazando los constructores encadenados/telescópicos por una API fluida y paso a paso. Se refactorizó un `Task` de nueve campos para usar una clase interna estática `Builder` con métodos setter con nombre y un método `build()` que produce el objeto final inmutable.

La contrapartida principal: el Builder añade verbosidad mediante campos y métodos duplicados, a cambio de ganancias importantes en legibilidad y flexibilidad en el punto de llamada. Para clases con muchos parámetros opcionales, esta contrapartida suele valer la pena.
