## 1. Overview

Builder is a **creational** pattern that solves a very practical problem: constructing objects with many fields, some of which are optional.

Modules:
- Start: `the-builder-pattern-start`
- End (reference solution): `the-builder-pattern-end`

## 2. The Problem: Telescoping Constructors

`Task` has nine fields: `id` (`Long`), `name` (`String`), `description` (`String`), `dueDate` (`LocalDate`), `status` (`TaskStatus`), `priority` (`Priority`), `assignee` (`String`), `project` (`String`), `estimatedHours` (`Double`).
`TaskStatus`: `TO_DO`, `IN_PROGRESS`, `ON_HOLD`, `DONE`. `Priority`: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.

To support creating a task with different combinations of optional fields, we'd need multiple constructor overloads — `Task(name)`, `Task(name, description)`, `Task(name, description, dueDate)`, and so on up to a full nine-parameter constructor. This is the **telescoping constructor anti-pattern**, and it creates two concrete problems.

**1. The call site is hard to read:**

```java
Task task = new Task(null, "Design login page",
        "Create wireframes and implement the login UI with OAuth support",
        LocalDate.of(2050, 6, 1), TaskStatus.TO_DO, Priority.HIGH,
        "Alice", "Website Redesign", 12.0);
```

With nine positional parameters, it's very hard to tell which argument maps to which field. Is `"Alice"` the assignee or the project? Is `12.0` the estimated hours or something else? Passing `null` for the ID is awkward, and swapping `"Alice"` for `"Website Redesign"` compiles fine since both are strings — the compiler can't catch that mistake.

**2. Every new optional field means another constructor overload.** The number of constructors grows fast and becomes unmanageable.

Builder solves both problems by replacing positional constructors with **named methods**.

## 3. What Is the Builder Pattern?

> A creational pattern that separates the construction of a complex object from its representation.

While Singleton controls *how many* instances of a class exist, Builder controls *how* an instance is constructed.

### 3.1. How It Solves the Problem

Instead of passing a long list of positional arguments to a constructor, we configure the object step by step and produce the final result when ready. From the caller's side: each parameter is **named**, order doesn't matter, and optional fields can simply be left out — the call site becomes self-documenting.

In this implementation, `Task` is also **immutable**: once built, it can't change. Natural pairing — Builder handles step-by-step construction, the finished `Task` locks down its state. Adding a new optional field later doesn't break existing callers; they simply don't call the new method.

### 3.2. Key Elements

| Element | Role |
|---|---|
| **Builder** | Separate object mirroring the product's fields |
| Fluent setters | Accumulate configuration, each returning `this` for chaining |
| `build()` | Takes accumulated state and produces the finished object |

## 4. Implementation

### 4.1. Updating the `Task` Class

Constructor becomes **private**, accepting a `Builder` and copying its fields; every field becomes **final**:

```java
public class Task {

    private final Long id;
    private final String name;
    private final String description;
    private final LocalDate dueDate;
    private final TaskStatus status;
    private final Priority priority;
    private final String assignee;
    private final String project;
    private final Double estimatedHours;

    private Task(Builder builder) {
        this.id = builder.id;
        this.name = builder.name;
        this.description = builder.description;
        this.dueDate = builder.dueDate;
        this.status = builder.status;
        this.priority = builder.priority;
        this.assignee = builder.assignee;
        this.project = builder.project;
        this.estimatedHours = builder.estimatedHours;
    }

    // standard getters
}
```

Compared to the start project: all setters are removed, every field is `final`. This is **not equivalent** to the original mutable `Task` with setter methods that could change any field post-construction — the new `Task` freezes its data at construction time. The private constructor forces callers through the `Builder`, and once built, a `Task` can't be modified.

### 4.2. Creating the Builder

A static inner class mirroring the same nine fields, each with a fluent setter:

```java
public static class Builder {

    private Long id;
    private final String name;
    private String description;
    private LocalDate dueDate;
    private TaskStatus status = TaskStatus.TO_DO;
    private Priority priority = Priority.MEDIUM;
    private String assignee;
    private String project;
    private Double estimatedHours;

    public Builder(String name) {
        this.name = name;
    }

    public Builder id(Long id) {
        this.id = id;
        return this;
    }

    public Builder description(String description) {
        this.description = description;
        return this;
    }

    public Builder dueDate(LocalDate dueDate) {
        this.dueDate = dueDate;
        return this;
    }

    public Builder status(TaskStatus status) {
        this.status = status;
        return this;
    }

    public Builder priority(Priority priority) {
        this.priority = priority;
        return this;
    }

    public Builder assignee(String assignee) {
        this.assignee = assignee;
        return this;
    }

    public Builder project(String project) {
        this.project = project;
        return this;
    }

    public Builder estimatedHours(Double estimatedHours) {
        this.estimatedHours = estimatedHours;
        return this;
    }

    public Task build() {
        return new Task(this);
    }
}
```

`name` is the only required parameter, accepted in the `Builder`'s own constructor — this guarantees every `Task` has at least a name. `status` defaults to `TaskStatus.TO_DO`, `priority` to `Priority.MEDIUM`; every other optional field defaults to `null`.

Each fluent method sets one field and returns `this` (method chaining). `build()` creates a new `Task` by passing the `Builder` itself to the private constructor.

> **Convention note:** a static inner `Builder` class is widely adopted in modern Java, popularized by *Effective Java*. It sits alongside its product class and can access the private constructor. (It could also be a separate top-level class, though the inner-class style is far more common.)

### 4.3. Testing

```java
class BuilderPatternUnitTest {

    @Test
    void givenAllFieldsSet_whenBuild_thenTaskHasAllValues() {
        Task task = new Task.Builder("Design login page")
                .id(1L)
                .description("Create wireframes and implement the login UI with OAuth support")
                .dueDate(LocalDate.of(2050, 6, 1))
                .status(TaskStatus.IN_PROGRESS)
                .priority(Priority.HIGH)
                .assignee("Alice")
                .project("Website Redesign")
                .estimatedHours(12.0)
                .build();

        assertEquals("Design login page", task.getName());
        assertEquals(1L, task.getId());
        assertEquals("Create wireframes and implement the login UI with OAuth support", task.getDescription());
        assertEquals(LocalDate.of(2050, 6, 1), task.getDueDate());
        assertEquals(TaskStatus.IN_PROGRESS, task.getStatus());
        assertEquals(Priority.HIGH, task.getPriority());
        assertEquals("Alice", task.getAssignee());
        assertEquals("Website Redesign", task.getProject());
        assertEquals(12.0, task.getEstimatedHours());
    }

    @Test
    void givenOnlyRequiredField_whenBuild_thenDefaultsApplied() {
        Task task = new Task.Builder("Quick task").build();

        assertEquals("Quick task", task.getName());
        assertEquals(TaskStatus.TO_DO, task.getStatus());
        assertEquals(Priority.MEDIUM, task.getPriority());
        assertNull(task.getId());
        assertNull(task.getDescription());
        assertNull(task.getDueDate());
        assertNull(task.getAssignee());
        assertNull(task.getProject());
        assertNull(task.getEstimatedHours());
    }
}
```

Compare the builder call to the telescoping constructor from Section 2: every parameter named, order irrelevant, optional fields simply omitted. The second test confirms defaults (`TO_DO`, `MEDIUM`) apply when only the required `name` is set, and every unspecified optional field is `null`.

> In production code, `build()` might also validate required fields (e.g., throw `IllegalStateException` if `name` is `null`) — kept simple here.

Run: `mvn test`.

## 5. When to Use / When Not to Use

### 5.1. Use it when
- A class has **four or more fields**, many of them optional — this is where the telescoping constructor problem becomes real.
- Construction involves **complex logic**: multiple steps, conditional defaults, or validation the Builder can encapsulate behind a clean API.
- The call site should be **self-documenting** — named methods make each parameter's intent explicit.

### 5.2. Avoid it when
- A class has only **two or three fields** — a straightforward constructor is clearer and more concise; Builder adds boilerplate with no real benefit.
- **Every field is required**, no optional parameters — a constructor communicates that constraint more directly. In modern Java, a **record** may be an even better fit.
- Each `build()` call allocates an extra `Builder` object — negligible in the vast majority of cases; only worth worrying about in extremely tight inner loops creating millions of objects, which is rarely a practical concern.

### 5.3. The Verbosity Trade-Off

The main drawback is **boilerplate** — the `Builder` class duplicates every field from the product class. For a nine-field `Task`, the `Builder` also has nine fields, nine setters, and a `build()` method: real duplication that grows linearly with field count.

Honest trade-off: verbosity in the class definition, in exchange for readability at the call site. Usually worth it for classes with many optional parameters. Modern IDEs can generate much of this boilerplate automatically, and libraries like **Lombok** generate the whole `Builder` with a single `@Builder` annotation — implemented manually here to understand the mechanics.

## 6. Real-World Builder Examples (JDK)

### 6.1. `StringBuilder`

Probably the most familiar Builder in Java — accumulates character data through chaining, produces the final `String` via `toString()`:

```java
String result = new StringBuilder()
        .append("Task: ")
        .append("Design login page")
        .append(" [")
        .append("IN_PROGRESS")
        .append("]")
        .toString();
```

Same pattern implemented above: construct step by step, produce the result at the end.

### 6.2. `HttpRequest.newBuilder()` (Java 11+)

A modern, fluent Builder API:

```java
HttpRequest request = HttpRequest.newBuilder(URI.create("https://api.example.com/tasks"))
        .header("Accept", "application/json")
        .GET()
        .build();
```

The static factory `newBuilder()` creates the Builder, fluent setters configure the request, `build()` produces an immutable `HttpRequest` — a textbook application of the static inner Builder style at the JDK level.

### 6.3. `Calendar.Builder` (Java 8+)

Replaces the error-prone `Calendar.set(field, value)` approach:

```java
Calendar calendar = new Calendar.Builder()
        .setDate(2050, Calendar.JUNE, 15)
        .setTimeZone(TimeZone.getDefault())
        .build();
```

The Builder enforces valid combinations and produces the final `Calendar` in one step, avoiding the partially-constructed state the old setter-based API allowed (a `Calendar` existing with some fields set and others left in an inconsistent default).

## 7. Conclusion

Builder separates object construction from its representation, replacing chained/telescoping constructors with a fluent, step-by-step API. A nine-field `Task` was refactored to use a static inner `Builder` class with named setter methods and a `build()` method producing the final immutable object.

The main trade-off: the Builder adds verbosity through duplicated fields and methods, in exchange for significant readability and flexibility gains at the call site. For classes with many optional parameters, this trade-off is usually worth it.
