## 1. Overview

The Decorator pattern lets us add behavior to objects dynamically by **wrapping them in other objects that share the same interface**, without modifying the original class.

Modules:
- Start: `the-decorator-pattern-start`
- End (reference solution): `the-decorator-pattern-end`

## 2. The Problem: Modifying Behavior Without Modifying Code

Domain model:
- `Task`: `id` (`Long`), `name` (`String`), `status` (`TaskStatus`), `createdAt` (`LocalDateTime`), `updatedAt` (`LocalDateTime`)
- `TaskRepository` interface: `save(Task)`, `findAll(): List<Task>`
- `InMemoryTaskRepository implements TaskRepository`, backed by a `HashMap<Long, Task>`

We need two cross-cutting behaviors:
1. `findAll()` should **cache** its results so the list isn't rebuilt on every call.
2. `save()` should automatically set `createdAt`/`updatedAt` timestamps before saving.

Crucially, we don't want to touch `InMemoryTaskRepository` — it should stay focused purely on storage.

**The inheritance approach:**
- `CachingInMemoryTaskRepository extends InMemoryTaskRepository` — adds caching to `findAll()`
- `TimestampingInMemoryTaskRepository extends InMemoryTaskRepository` — adds timestamps to `save()`

But what if we need **both** behaviors at once? We'd need `CachingTimestampingInMemoryTaskRepository`. The problem only grows: with **3** independent behaviors we'd need **7** subclasses (3 single + 3 pairs + 1 triple); with **4**, **15**. Inheritance doesn't scale for optional, combinable behaviors — each new behavior **doubles** the number of combinations, and every combination needs its own class.

Second problem: these subclasses are tied specifically to `InMemoryTaskRepository`. Adding a `DatabaseTaskRepository` later means duplicating the entire subclass hierarchy.

This is a case where **composition beats inheritance**. We need to layer behaviors dynamically at runtime instead of baking them into a class hierarchy. The Decorator pattern solves exactly this.

## 3. The Decorator Pattern

> A **structural** pattern that adds new behavior to an object dynamically by wrapping it in another object with the same interface.

### 3.1. How It Solves the Problem

Instead of subclassing for every combination, we **compose behaviors at runtime** by stacking wrappers around a base object. From the client's perspective the difference is invisible — it doesn't care whether it's talking to the original object or a decorated version, since both implement the same interface. Any code using a `TaskRepository` can accept a decorated version with zero changes.

The class explosion disappears entirely: instead of 7 subclasses for 3 behaviors, we write **3 decorator classes** and combine them freely at runtime. Adding a new behavior means writing one new class, not duplicating the hierarchy. The base implementation stays untouched — `InMemoryTaskRepository` keeps doing only storage. A future `DatabaseTaskRepository` works with the same decorators, since they depend on the `TaskRepository` interface, not on any specific implementation.

### 3.2. Key Elements and Mechanism

A decorator implements the same interface as the component it wraps, holds a reference to that component, adds its own behavior in the relevant methods, and **delegates everything else** to the wrapped object.

GoF participants:

| Role | In this example |
|---|---|
| **Component** | `TaskRepository` interface |
| **ConcreteComponent** | `InMemoryTaskRepository` |
| **Decorator** | abstract concept: implements `Component`, holds a `Component` reference, delegates while adding behavior |
| **ConcreteDecorator** | `CachingTaskRepositoryDecorator`, `TimestampingTaskRepositoryDecorator` |

These elements replace inheritance-based extension with **runtime composition**: the decorator holds a reference to the wrapped component, intercepts calls, and layers its own behavior on top of delegation.

## 4. Implementation

### 4.1. Implementing and Using a Single Decorator

```java
public class CachingTaskRepositoryDecorator implements TaskRepository {

    private final TaskRepository wrapped;
    private List<Task> cache;

    public CachingTaskRepositoryDecorator(TaskRepository wrapped) {
        this.wrapped = wrapped;
    }

    @Override
    public void save(Task task) {
        wrapped.save(task);
        cache = null;
    }

    @Override
    public List<Task> findAll() {
        if (cache == null) {
            cache = wrapped.findAll();
        }
        return cache;
    }
}
```

Mechanics: the constructor receives the `TaskRepository` being wrapped. `cache` starts as `null` (no data fetched yet). `findAll()` checks whether the cache is empty; if so, it delegates to the wrapped repository's `findAll()` and stores the result — subsequent calls return the cached list directly without touching the wrapped repository. `save()` delegates to the wrapped repository, then **invalidates the cache** by setting it to `null`, guaranteeing the next `findAll()` picks up fresh data reflecting what was just saved.

Key point: `InMemoryTaskRepository` isn't modified at all. Caching lives entirely in its own class. Any code working with `TaskRepository` can use `CachingTaskRepositoryDecorator` transparently.

```java
class DecoratorPatternUnitTest {

    @Test
    void givenCachingDecorator_whenFindAllCalledTwice_thenReturnsSameData() {
        TaskRepository base = new InMemoryTaskRepository();
        TaskRepository cached = new CachingTaskRepositoryDecorator(base);

        Task task = new Task(1L, "Design review", TaskStatus.TO_DO);
        cached.save(task);

        List<Task> firstCall = cached.findAll();
        List<Task> secondCall = cached.findAll();

        assertEquals(1, firstCall.size());
        assertSame(firstCall, secondCall);
    }
}
```

`assertSame()` confirms both calls return the **same list instance**, proving the cache works — without it, every `findAll()` call would build a fresh list from the underlying repository.

### 4.2. Composing Decorators

```java
public class TimestampingTaskRepositoryDecorator implements TaskRepository {

    private final TaskRepository wrapped;

    public TimestampingTaskRepositoryDecorator(TaskRepository wrapped) {
        this.wrapped = wrapped;
    }

    @Override
    public void save(Task task) {
        if (task.getCreatedAt() == null) {
            task.setCreatedAt(LocalDateTime.now());
        }
        task.setUpdatedAt(LocalDateTime.now());
        wrapped.save(task);
    }

    @Override
    public List<Task> findAll() {
        return wrapped.findAll();
    }
}
```

Note `findAll()` is pure pass-through — it exists only because `TaskRepository` requires it. Manageable with a two-method interface, but forwarding boilerplate grows quickly with larger interfaces. An **abstract decorator base class** implementing every method as a pass-through (so concrete decorators only override what they care about) helps here; for this small interface, direct implementation is simpler.

**Stacking decorators:**

```java
TaskRepository base = new InMemoryTaskRepository();
TaskRepository repository = new TimestampingTaskRepositoryDecorator(base);
repository = new CachingTaskRepositoryDecorator(repository);
```

Wrap `InMemoryTaskRepository` in `TimestampingTaskRepositoryDecorator`, then wrap *that* in `CachingTaskRepositoryDecorator` — a single `TaskRepository` reference that timestamps on save and caches on find.

> **Wrapping order determines execution order.** The outermost decorator intercepts first. In the stack above, a `save()` call hits the caching decorator first (invalidating its cache), flows to the timestamping decorator (setting timestamps), and finally reaches `InMemoryTaskRepository`.

```java
@Test
void givenStackedDecorators_whenSaveAndFind_thenBothBehaviorsApply() {
    TaskRepository base = new InMemoryTaskRepository();
    TaskRepository repository = new TimestampingTaskRepositoryDecorator(base);
    repository = new CachingTaskRepositoryDecorator(repository);

    Task task = new Task(1L, "Design review", TaskStatus.TO_DO);
    repository.save(task);

    assertNotNull(task.getCreatedAt());
    assertNotNull(task.getUpdatedAt());
    assertEquals(1, repository.findAll().size());
    assertSame(repository.findAll(), repository.findAll());
}
```

For these two decorators, order doesn't affect correctness — but in general it **can** matter (e.g., encryption vs. compression decorators produce different results depending on which runs first).

**Conditional dynamic decoration** — choosing decorators at runtime via flags instead of hard-coding the stack:

```java
TaskRepository repository = new InMemoryTaskRepository();
if (timestampingEnabled) {
    repository = new TimestampingTaskRepositoryDecorator(repository);
}
if (cachingEnabled) {
    repository = new CachingTaskRepositoryDecorator(repository);
}
```

This is the pattern's core power: behaviors composed at runtime, not baked into a class hierarchy. Caching and timestamping toggle independently with **zero additional classes** — contrast with the inheritance approach of Section 2, where every combination needed a dedicated subclass.

> **Trade-off to note:** stacking multiple decorators deepens stack traces — a `save()` call passes through every wrapper before reaching `InMemoryTaskRepository`. Manageable for two or three decorators; harder to trace with many layers. Not a dealbreaker, but worth knowing.

Run: `mvn test`.

### 4.3. SOLID Principles at Work

- **Open/Closed Principle** — new behaviors are added via new decorator classes, never by modifying existing ones.
- **Liskov Substitution Principle** — the structural foundation that makes the pattern possible. Every decorator must be fully substitutable for the component it wraps; because `CachingTaskRepositoryDecorator implements TaskRepository` and honors its contract, any code expecting a `TaskRepository` can accept the decorated version without knowing the difference. If a decorator violated LSP by changing the expected behavior of interface methods, the pattern would break down.
- **Dependency Inversion Principle** — gives decorators their reusability. Decorators depend on the `TaskRepository` abstraction, not on `InMemoryTaskRepository` directly — the same `CachingTaskRepositoryDecorator` can wrap *any* `TaskRepository` implementation (in-memory, database-backed, or even another decorator).

Together: OCP means existing classes are never modified to add behavior; LSP means the decorated object is indistinguishable from the original; DIP means decorators are reusable across any interface implementation.

## 5. When to Use It / When Not To

### 5.1. Use it when
- Responsibilities must be added to objects **dynamically at runtime**, with combinations unknown at compile time.
- Extending behavior through inheritance would cause a **class explosion** (Section 2).
- Behaviors should be **optional and independently toggleable** (e.g., caching and timestamping flags).
- Open/Closed compliance matters — new behavior via new decorators, no existing-code changes.

### 5.2. Avoid it when
- The behavior is **always required**, never optional — just build it directly into the class.
- The interface is **large** — the forwarding burden (every decorator implementing every method) becomes significant.
- **Transparency hurts debuggability** — decorators are invisible to the client by design, which can make comprehension harder when that matters a lot.
- A single, fixed enhancement suffices and there's no need for dynamic composition — a simple wrapper or subclass may be clearer.

## 6. Real-World Usage

### 6.1. `BufferedInputStream` Wrapping `FileInputStream`

A classic JDK Decorator:

```java
InputStream fileStream = new FileInputStream("tasks.csv");
InputStream buffered = new BufferedInputStream(fileStream);
```

| Role | Class |
|---|---|
| Component | `InputStream` |
| ConcreteComponent | `FileInputStream` |
| ConcreteDecorator | `BufferedInputStream` |

`BufferedInputStream` reads a chunk of bytes into an internal buffer and serves subsequent `read()` calls from it, reducing expensive I/O operations (reading from memory is far cheaper than disk, one byte at a time). Same interface, component injected via constructor, transparent behavior addition — all decorator hallmarks.

Java's entire I/O library is built on decorator stacking: `new DataInputStream(new BufferedInputStream(new FileInputStream("data.bin")))` layers typed reading on top of buffering on top of file access — each wrapper adding a capability, composed at construction time.

### 6.2. `Collections.synchronizedList()`

Wraps a `List` in a decorator that synchronizes every method call, adding thread-safety without modifying the original list — same interface, holds a reference to the wrapped list, delegates every method inside a `synchronized` block.

> `Collections.unmodifiableList()` has a similar structure but different *intent*: it **restricts** access rather than adding behavior — closer to the **Proxy** pattern.

## 7. Related Patterns

### 7.1. Decorator vs. Adapter

Both wrap an object and implement an interface, but intent differs:
- **Adapter** changes the interface — makes an incompatible class conform to an expected one.
- **Decorator** keeps the same interface — adds behavior while preserving the original contract.

> **Rule of thumb:** if the wrapper changes how the object *looks* to the client → Adapter. If it changes what the object *does*, same interface → Decorator.

### 7.2. Decorator vs. Proxy

Structurally very similar — both implement the same interface as the wrapped object and delegate to it. The difference is **purpose**: a Decorator **adds new functionality** (caching, timestamping, buffering); a Proxy **controls access** to the object (lazy initialization, access checks).

In practice the line can blur, and intent is what determines the classification. (Proxy is covered in a later lesson.)

> **A broader GoF distinction:** Decorator changes an object's "look" (external behavior), while **Strategy** changes its "insides" (internal algorithm). Both achieve behavior variation, but through different mechanisms — wrapping from outside vs. swapping from inside.

## 8. Conclusion

The Decorator pattern lets us add behavior to objects dynamically by wrapping them in objects sharing the same interface. We built `CachingTaskRepositoryDecorator` and `TimestampingTaskRepositoryDecorator` and saw how they stack and toggle at runtime without touching the original `InMemoryTaskRepository`.

Main advantage: behaviors compose at runtime without a class explosion or modifying existing code. Downsides exist but are manageable — forwarding burden grows with larger interfaces, and stacked decorators deepen stack traces. As a design tool, Decorator is one of the clearest practical demonstrations of **composition over inheritance**.
