## 1. Descripción general

El patrón Decorator permite añadir comportamiento a los objetos de forma dinámica **envolviéndolos en otros objetos que comparten la misma interfaz**, sin modificar la clase original.

Módulos:
- Inicio: `the-decorator-pattern-start`
- Fin (solución de referencia): `the-decorator-pattern-end`

## 2. El problema: modificar comportamiento sin modificar código

Modelo de dominio:
- `Task`: `id` (`Long`), `name` (`String`), `status` (`TaskStatus`), `createdAt` (`LocalDateTime`), `updatedAt` (`LocalDateTime`)
- Interfaz `TaskRepository`: `save(Task)`, `findAll(): List<Task>`
- `InMemoryTaskRepository implements TaskRepository`, respaldado por un `HashMap<Long, Task>`

Necesitamos dos comportamientos transversales:
1. `findAll()` debe **almacenar en caché** sus resultados para no reconstruir la lista en cada llamada.
2. `save()` debe establecer automáticamente las marcas de tiempo `createdAt`/`updatedAt` antes de guardar.

Fundamentalmente, no queremos tocar `InMemoryTaskRepository` — debe seguir centrado exclusivamente en el almacenamiento.

**El enfoque basado en herencia:**
- `CachingInMemoryTaskRepository extends InMemoryTaskRepository` — agrega caché a `findAll()`
- `TimestampingInMemoryTaskRepository extends InMemoryTaskRepository` — agrega marcas de tiempo a `save()`

Pero ¿qué pasa si necesitamos **ambos** comportamientos a la vez? Necesitaríamos `CachingTimestampingInMemoryTaskRepository`. El problema no hace más que crecer: con **3** comportamientos independientes necesitaríamos **7** subclases (3 individuales + 3 pares + 1 triple); con **4**, serían **15**. La herencia no escala para comportamientos opcionales y combinables — cada nuevo comportamiento **duplica** el número de combinaciones, y cada combinación requiere su propia clase.

Segundo problema: estas subclases están vinculadas específicamente a `InMemoryTaskRepository`. Si más adelante añadimos un `DatabaseTaskRepository`, habría que duplicar toda la jerarquía de subclases.

Este es un caso donde la **composición supera a la herencia**. Necesitamos superponer comportamientos dinámicamente en tiempo de ejecución en lugar de incorporarlos a una jerarquía de clases. El patrón Decorator resuelve precisamente esto.

## 3. El patrón Decorator

> Un patrón **estructural** que añade dinámicamente nuevo comportamiento a un objeto envolviéndolo en otro objeto con la misma interfaz.

### 3.1. Cómo resuelve el problema

En lugar de crear subclases para cada combinación, **componemos comportamientos en tiempo de ejecución** apilando envoltorios alrededor de un objeto base. Desde la perspectiva del cliente, la diferencia es imperceptible — no le importa si habla con el objeto original o con una versión decorada, ya que ambos implementan la misma interfaz. Cualquier código que use un `TaskRepository` puede aceptar una versión decorada sin ningún cambio.

La explosión de clases desaparece por completo: en lugar de 7 subclases para 3 comportamientos, escribimos **3 clases decoradoras** y las combinamos libremente en tiempo de ejecución. Agregar un nuevo comportamiento implica escribir una sola clase nueva, no duplicar la jerarquía. La implementación base permanece intacta — `InMemoryTaskRepository` sigue haciendo solo almacenamiento. Un futuro `DatabaseTaskRepository` funcionará con los mismos decoradores, ya que estos dependen de la interfaz `TaskRepository`, no de ninguna implementación específica.

### 3.2. Elementos clave y mecanismo

Un decorador implementa la misma interfaz que el componente que envuelve, mantiene una referencia a dicho componente, agrega su propio comportamiento en los métodos correspondientes y **delega todo lo demás** al objeto envuelto.

Participantes GoF:

| Rol | En este ejemplo |
|---|---|
| **Component** | interfaz `TaskRepository` |
| **ConcreteComponent** | `InMemoryTaskRepository` |
| **Decorator** | concepto abstracto: implementa `Component`, mantiene una referencia a un `Component`, delega mientras agrega comportamiento |
| **ConcreteDecorator** | `CachingTaskRepositoryDecorator`, `TimestampingTaskRepositoryDecorator` |

Estos elementos reemplazan la extensión basada en herencia con **composición en tiempo de ejecución**: el decorador mantiene una referencia al componente envuelto, intercepta las llamadas, y superpone su propio comportamiento sobre la delegación.

## 4. Implementación

### 4.1. Implementación y uso de un solo decorador

```java
public class CachingTaskRepositoryDecorator implements TaskRepository {

    private final TaskRepository wrapped;
    private List<Task> cache;

    public CachingTaskRepositoryDecorator(TaskRepository wrapped) {
        this.wrapped = wrapped;
    }

    @Override
    public void save(Task task) {
        wrapped.save(task);
        cache = null;
    }

    @Override
    public List<Task> findAll() {
        if (cache == null) {
            cache = wrapped.findAll();
        }
        return cache;
    }
}
```

Mecánica: el constructor recibe el `TaskRepository` que se está envolviendo. `cache` comienza como `null` (aún no se han obtenido datos). `findAll()` comprueba si la caché está vacía; si es así, delega al `findAll()` del repositorio envuelto y almacena el resultado — en llamadas posteriores devuelve la lista cacheada directamente sin tocar el repositorio envuelto. `save()` delega en el repositorio envuelto y luego **invalida la caché** estableciéndola en `null`, garantizando que la siguiente llamada a `findAll()` obtenga datos frescos que reflejen lo que se acaba de guardar.

Punto clave: `InMemoryTaskRepository` no se modifica en absoluto. El comportamiento de caché vive por completo en su propia clase. Cualquier código que trabaje con `TaskRepository` puede usar `CachingTaskRepositoryDecorator` de forma transparente.

```java
class DecoratorPatternUnitTest {

    @Test
    void givenCachingDecorator_whenFindAllCalledTwice_thenReturnsSameData() {
        TaskRepository base = new InMemoryTaskRepository();
        TaskRepository cached = new CachingTaskRepositoryDecorator(base);

        Task task = new Task(1L, "Design review", TaskStatus.TO_DO);
        cached.save(task);

        List<Task> firstCall = cached.findAll();
        List<Task> secondCall = cached.findAll();

        assertEquals(1, firstCall.size());
        assertSame(firstCall, secondCall);
    }
}
```

`assertSame()` confirma que ambas llamadas devuelven la **misma instancia de lista**, probando que la caché funciona — sin ella, cada llamada a `findAll()` construiría una lista nueva a partir del repositorio subyacente.

### 4.2. Composición de decoradores

```java
public class TimestampingTaskRepositoryDecorator implements TaskRepository {

    private final TaskRepository wrapped;

    public TimestampingTaskRepositoryDecorator(TaskRepository wrapped) {
        this.wrapped = wrapped;
    }

    @Override
    public void save(Task task) {
        if (task.getCreatedAt() == null) {
            task.setCreatedAt(LocalDateTime.now());
        }
        task.setUpdatedAt(LocalDateTime.now());
        wrapped.save(task);
    }

    @Override
    public List<Task> findAll() {
        return wrapped.findAll();
    }
}
```

Nótese que `findAll()` es un simple *pass-through* — existe solo porque `TaskRepository` lo exige. Manejable con una interfaz de dos métodos, pero el boilerplate de reenvío crece rápidamente con interfaces más grandes. Una **clase base abstracta de decorador** que implemente todos los métodos como pass-through (dejando que los decoradores concretos sobrescriban solo lo que les importa) ayuda aquí; para esta interfaz pequeña, la implementación directa es más simple.

**Apilando decoradores:**

```java
TaskRepository base = new InMemoryTaskRepository();
TaskRepository repository = new TimestampingTaskRepositoryDecorator(base);
repository = new CachingTaskRepositoryDecorator(repository);
```

Envolvemos `InMemoryTaskRepository` en `TimestampingTaskRepositoryDecorator`, y luego envolvemos *eso* en `CachingTaskRepositoryDecorator` — una única referencia `TaskRepository` que marca con timestamps al guardar y cachea al buscar.

> **El orden de envoltura determina el orden de ejecución.** El decorador más externo intercepta primero. En la pila anterior, una llamada a `save()` llega primero al decorador de caché (que invalida su caché), fluye hacia el decorador de timestamps (que establece las marcas de tiempo), y finalmente llega a `InMemoryTaskRepository`.

```java
@Test
void givenStackedDecorators_whenSaveAndFind_thenBothBehaviorsApply() {
    TaskRepository base = new InMemoryTaskRepository();
    TaskRepository repository = new TimestampingTaskRepositoryDecorator(base);
    repository = new CachingTaskRepositoryDecorator(repository);

    Task task = new Task(1L, "Design review", TaskStatus.TO_DO);
    repository.save(task);

    assertNotNull(task.getCreatedAt());
    assertNotNull(task.getUpdatedAt());
    assertEquals(1, repository.findAll().size());
    assertSame(repository.findAll(), repository.findAll());
}
```

Para estos dos decoradores, el orden no afecta la corrección — pero en general **sí puede importar** (p. ej., decoradores de encriptación vs. compresión producen resultados distintos según cuál se ejecute primero).

**Decoración dinámica condicional** — elegir decoradores en tiempo de ejecución mediante flags en lugar de fijar el orden de envoltura:

```java
TaskRepository repository = new InMemoryTaskRepository();
if (timestampingEnabled) {
    repository = new TimestampingTaskRepositoryDecorator(repository);
}
if (cachingEnabled) {
    repository = new CachingTaskRepositoryDecorator(repository);
}
```

Este es el poder central del patrón: los comportamientos se componen en tiempo de ejecución, no se incorporan a una jerarquía de clases. Caché y timestamps se activan/desactivan de forma independiente con **cero clases adicionales** — contrástese con el enfoque de herencia de la Sección 2, donde cada combinación necesitaba una subclase dedicada.

> **Contrapartida a tener en cuenta:** apilar varios decoradores profundiza los stack traces — una llamada a `save()` pasa por cada envoltorio antes de llegar a `InMemoryTaskRepository`. Manejable con dos o tres decoradores; más difícil de rastrear con muchas capas. No es un impedimento, pero vale la pena saberlo.

Ejecutar: `mvn test`.

### 4.3. Principios SOLID en juego

- **Principio Abierto/Cerrado** — los comportamientos nuevos se agregan mediante nuevas clases decoradoras, nunca modificando las existentes.
- **Principio de Sustitución de Liskov** — el fundamento estructural que hace posible el patrón. Todo decorador debe ser completamente sustituible por el componente que envuelve; como `CachingTaskRepositoryDecorator implements TaskRepository` y respeta su contrato, cualquier código que espere un `TaskRepository` puede aceptar la versión decorada sin notar la diferencia. Si un decorador violara LSP cambiando el comportamiento esperado de los métodos de la interfaz, el patrón se rompería por completo.
- **Principio de Inversión de Dependencias** — da a los decoradores su reutilización. Los decoradores dependen de la abstracción `TaskRepository`, no directamente de `InMemoryTaskRepository` — el mismo `CachingTaskRepositoryDecorator` puede envolver *cualquier* implementación de `TaskRepository` (en memoria, respaldada por base de datos, o incluso otro decorador).

En conjunto: OCP implica que las clases existentes nunca se modifican para agregar comportamiento; LSP implica que el objeto decorado es indistinguible del original; DIP implica que los decoradores son reutilizables en cualquier implementación de la interfaz.

## 5. Cuándo usarlo / cuándo no

### 5.1. Úsalo cuando
- Hay que agregar responsabilidades a los objetos **dinámicamente en tiempo de ejecución**, con combinaciones desconocidas en tiempo de compilación.
- Extender el comportamiento mediante herencia causaría una **explosión de clases** (Sección 2).
- Los comportamientos deben ser **opcionales y alternables de forma independiente** (p. ej., los flags de caché y timestamps).
- Importa el cumplimiento del Principio Abierto/Cerrado — comportamiento nuevo vía nuevos decoradores, sin cambios al código existente.

### 5.2. Evítalo cuando
- El comportamiento es **siempre obligatorio**, nunca opcional — simplemente incorpóralo directamente a la clase.
- La interfaz es **grande** — la carga de reenvío (cada decorador implementando cada método) se vuelve significativa.
- **La transparencia perjudica la depurabilidad** — los decoradores son invisibles para el cliente por diseño, lo cual puede dificultar la comprensión cuando eso importa mucho.
- Basta con una mejora única y fija, sin necesidad de composición dinámica — un simple wrapper o subclase puede ser más claro.

## 6. Uso en el mundo real

### 6.1. `BufferedInputStream` envolviendo a `FileInputStream`

Un Decorator clásico del JDK:

```java
InputStream fileStream = new FileInputStream("tasks.csv");
InputStream buffered = new BufferedInputStream(fileStream);
```

| Rol | Clase |
|---|---|
| Component | `InputStream` |
| ConcreteComponent | `FileInputStream` |
| ConcreteDecorator | `BufferedInputStream` |

`BufferedInputStream` lee un bloque de bytes del stream subyacente hacia un búfer interno, y atiende las siguientes llamadas a `read()` desde ese búfer, reduciendo las operaciones de E/S costosas (leer de memoria es mucho más barato que leer del disco byte por byte). Misma interfaz, componente inyectado por constructor, adición transparente de comportamiento — todas las características distintivas del decorador.

Toda la biblioteca de E/S de Java está construida sobre apilamiento de decoradores: `new DataInputStream(new BufferedInputStream(new FileInputStream("data.bin")))` superpone lectura tipada sobre buffering sobre acceso a archivo — cada envoltorio agrega una capacidad, compuesta en el momento de la construcción.

### 6.2. `Collections.synchronizedList()`

Envuelve una `List` en un decorador que sincroniza cada llamada a método, agregando seguridad para hilos sin modificar la lista original — misma interfaz, mantiene una referencia a la lista envuelta, delega cada método dentro de un bloque `synchronized`.

> `Collections.unmodifiableList()` tiene una estructura similar pero una *intención* distinta: **restringe** el acceso en lugar de agregar comportamiento — más cercano al patrón **Proxy**.

## 7. Patrones relacionados

### 7.1. Decorator vs. Adapter

Ambos envuelven un objeto e implementan una interfaz, pero la intención difiere:
- **Adapter** cambia la interfaz — hace que una clase incompatible se ajuste a una interfaz esperada.
- **Decorator** mantiene la misma interfaz — agrega comportamiento preservando el contrato original.

> **Regla práctica:** si el envoltorio cambia cómo *se ve* el objeto para el cliente → Adapter. Si cambia lo que el objeto *hace*, manteniendo la misma interfaz → Decorator.

### 7.2. Decorator vs. Proxy

Estructuralmente muy similares — ambos implementan la misma interfaz que el objeto envuelto y delegan en él. La diferencia está en el **propósito**: un Decorator **agrega nueva funcionalidad** (caché, timestamps, buffering); un Proxy **controla el acceso** al objeto (inicialización diferida, comprobaciones de acceso).

En la práctica la línea puede ser difusa, y la intención es lo que determina la clasificación. (Proxy se cubre en una lección posterior.)

> **Una distinción GoF más amplia:** Decorator cambia la "apariencia" de un objeto (comportamiento externo), mientras que **Strategy** cambia su "interior" (algoritmo interno). Ambos logran variación de comportamiento, pero mediante mecanismos diferentes — envoltura desde fuera frente a intercambio desde dentro.

## 8. Conclusión

El patrón Decorator permite agregar comportamiento a los objetos de forma dinámica envolviéndolos en objetos que comparten la misma interfaz. Construimos `CachingTaskRepositoryDecorator` y `TimestampingTaskRepositoryDecorator`, y vimos cómo se apilan y alternan en tiempo de ejecución sin tocar el `InMemoryTaskRepository` original.

Ventaja principal: los comportamientos se componen en tiempo de ejecución sin explosión de clases ni modificación del código existente. Existen desventajas, pero son manejables — la carga de reenvío crece con interfaces más grandes, y los decoradores apilados profundizan los stack traces. Como herramienta de diseño, Decorator es una de las demostraciones prácticas más claras de la **composición sobre la herencia**.
