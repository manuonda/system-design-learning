# Aprende Patrones de Diseño — Módulo 2, Lección 1: El Patrón Adapter

> Notas resumen de `the-adapter-pattern-start` / `the-adapter-pattern-end` (curso "Learn Design Patterns" de Baeldung).

## 1. La idea en una frase

> **Convertir la interfaz de una clase existente en otra interfaz que el cliente espera, sin modificar ninguna de las dos.** (GoF, 1994)

El Adapter **no crea** la interfaz nueva: la interfaz `Target` ya existe (la define tu sistema). El Adapter es el "traductor" que hace que una clase que **no podés tocar** (`Adaptee`) encaje en esa interfaz.

También se lo conoce como **Wrapper** (envoltorio).

## 2. Analogía: el adaptador de enchufe

| Mundo real | Patrón |
|---|---|
| El tomacorriente de la pared (espera 3 patas) | **Target** |
| El cargador de tu notebook (2 patas planas) | **Adaptee** |
| El adaptador de enchufe | **Adapter** |
| Vos, que querés enchufar | **Client** |

El adaptador **no cambia** la electricidad ni el cargador. Solo cambia la **forma** de conectarlos. Lo mismo en código: el Adapter cambia *cómo accedemos* al Adaptee, no *lo que hace*.

## 3. Los 4 participantes

| Rol | Qué es | En el ejemplo de Trello |
|---|---|---|
| **Target** | La interfaz de la que depende el cliente | `TaskImporter` |
| **Adaptee** | La clase existente con interfaz incompatible (no se puede modificar) | `TrelloClient` |
| **Adapter** | Implementa `Target` y envuelve al `Adaptee` | `TrelloTaskAdapter` |
| **Client** | Usa solo `Target`, no sabe nada del `Adaptee` | Código que llama a `importTasks()` |

```
Client ──usa──▶ «interface» Target ◀──implements── Adapter ──tiene un──▶ Adaptee
                  operation()                       operation() {         specificOperation()
                                                      adaptee.specificOperation()
                                                      + traducir datos
                                                    }
```

## 4. Ejemplo mínimo (para entender la mecánica)

Tu sistema espera temperaturas en Celsius, pero la librería de terceros devuelve Fahrenheit.

```java
// Target: lo que tu sistema espera
public interface CelsiusThermometer {
    double getCelsius();
}

// Adaptee: librería de terceros, no se puede modificar
public class FahrenheitSensor {
    public double readFahrenheit() {
        return 98.6;
    }
}

// Adapter: implementa Target, envuelve Adaptee y traduce
public class FahrenheitToCelsiusAdapter implements CelsiusThermometer {

    private final FahrenheitSensor sensor;

    public FahrenheitToCelsiusAdapter(FahrenheitSensor sensor) {
        this.sensor = sensor;
    }

    @Override
    public double getCelsius() {
        return (sensor.readFahrenheit() - 32) * 5 / 9;
    }
}

// Client: solo conoce CelsiusThermometer
CelsiusThermometer thermometer = new FahrenheitToCelsiusAdapter(new FahrenheitSensor());
thermometer.getCelsius(); // 37.0
```

Los tres pasos que hace todo Adapter:
1. **Implementa** el `Target`.
2. **Delega** la llamada al `Adaptee`.
3. **Traduce** el resultado (nombres, tipos, formatos, valores faltantes).

## 5. Ejemplo del curso: importar tareas desde Trello

### 5.1. El desajuste

`TrelloClient.fetchCards()` devuelve `List<TrelloCard>`, pero `TaskImporter.importTasks()` debe devolver `List<Task>`.

| `TrelloCard` (Adaptee) | `Task` (Target) | Tipo de traducción |
|---|---|---|
| `cardId` | `sourceId` | Mismo tipo, distinto nombre |
| `name` | `title` | Mismo tipo, distinto nombre |
| `description` | `description` | Directa |
| `listName` (`String` libre) | `status` (`TaskStatus` enum) | Conversión de tipo |
| — | `priority` | No existe → valor por defecto `"NORMAL"` |

### 5.2. El Adapter (Object Adapter, por composición)

```java
public class TrelloTaskAdapter implements TaskImporter {

    private final TrelloClient trelloClient;

    public TrelloTaskAdapter(TrelloClient trelloClient) {
        this.trelloClient = trelloClient;
    }

    @Override
    public List<Task> importTasks() {
        return trelloClient.fetchCards()
          .stream()
          .map(this::toTask)
          .toList();
    }

    private Task toTask(TrelloCard card) {
        return new Task(
          card.getName(),
          card.getDescription(),
          mapStatus(card.getListName()),
          card.getCardId(),
          "NORMAL");
    }

    private TaskStatus mapStatus(String listName) {
        return switch (listName) {
        case "To Do" -> TaskStatus.TO_DO;
        case "In Progress" -> TaskStatus.IN_PROGRESS;
        case "Done" -> TaskStatus.DONE;
        default -> TaskStatus.TO_DO;
        };
    }
}
```

Puntos clave:
- El `TrelloClient` se **inyecta por constructor** (composición). Eso define al *Object Adapter*.
- Toda la traducción vive en **una sola clase**. Ni `TrelloClient` ni `TaskImporter` cambian.
- Datos que no encajan: se usa **valor por defecto** (`priority = "NORMAL"`, listas desconocidas como `"Review"` → `TO_DO`) o se **lanza excepción** si la integridad es crítica.

### 5.3. Test: el cliente usa la interfaz, no el Adapter

```java
TaskImporter taskImporter = new TrelloTaskAdapter(new TrelloClient());

Task first = taskImporter.importTasks().getFirst();
assertEquals("Design homepage", first.getTitle());
assertEquals(TaskStatus.TO_DO, first.getStatus());
assertEquals("card-1", first.getSourceId());
assertEquals("NORMAL", first.getPriority());
```

## 6. Object Adapter vs. Class Adapter

| | Object Adapter | Class Adapter |
|---|---|---|
| Mecanismo | Composición (`has-a`) | Herencia (`extends TrelloClient implements TaskImporter`) |
| Acoplamiento | Bajo: acepta `TrelloClient` o cualquier subclase (ej. un mock) | Alto: atado a `TrelloClient` concreto |
| Herencia simple de Java | No consume el `extends` | Gasta el único `extends` |
| Recomendado | ✅ Sí | Solo como referencia |

```java
// Class Adapter: hereda fetchCards() y lo llama directo
public class TrelloTaskClassAdapter extends TrelloClient implements TaskImporter {

    @Override
    public List<Task> importTasks() {
        return fetchCards().stream().map(this::toTask).toList();
    }
}
```

Regla: **composición sobre herencia** (GoF, p. 20).

## 7. Variantes

- **Pluggable Adapter**: en vez de una clase Adapter, el lado Target recibe un callback (ej. `Supplier<List<Task>>`) y el cliente pasa la lógica como lambda. Útil para adaptaciones livianas.
  ```java
  Supplier<List<Task>> importer = () -> trelloClient.fetchCards().stream().map(...).toList();
  ```
- **Múltiples Adapters**: un Adapter por cada Target. Ej: `TrelloTaskAdapter` y `TrelloProjectAdapter`, ambos envolviendo `TrelloClient`.
- **Two-way Adapter**: implementa **ambas** interfaces (Target y Adaptee), para poder usarse en cualquiera de los dos roles. Más complejo, poco común.

## 8. SOLID en acción

| Principio | Cómo se cumple |
|---|---|
| **SRP** | El Adapter solo traduce. No guarda estado ni decide negocio. |
| **OCP** | Nueva fuente (Jira) → nuevo `JiraTaskAdapter`. No se toca código existente. |
| **LSP** | `TrelloTaskAdapter` cumple el contrato completo de `TaskImporter`. |
| **ISP** | `TaskImporter` es chica: solo lo que el cliente necesita. |
| **DIP** | El cliente depende de la abstracción `TaskImporter`, no de `TrelloClient`. |

## 9. Pros y contras

**Pros**
- Desacopla al cliente del Adaptee concreto.
- No invasivo: ni Target ni Adaptee cambian.
- Traducción centralizada en un solo lugar.
- Extensible: nueva fuente = nuevo Adapter.

**Contras**
- Una capa extra de indirección.
- Valores por defecto "ocultos" (ej. `priority`) pueden sorprender.
- Class Adapter limitado por herencia simple.
- Si la diferencia es **semántica** (no solo estructural), el Adapter se infla.

## 10. ¿Cuándo usarlo?

**Sí**
- Integrar librerías de terceros (el caso Trello).
- Integrar sistemas legacy.
- Migrar gradualmente de una interfaz vieja a una nueva.

**No**
- Controlás ambos lados → cambiá una de las interfaces. *Excepción*: si la clase la usan varios clientes con interfaces distintas, no la deformes para uno; escribí un Adapter.
- El desajuste es trivial (un rename) → una method reference o delegación inline alcanza.
- Ojo: no todo lo que se llama "Adapter" es GoF (ej. `RecyclerView.Adapter` de Android es binding de UI).

## 11. Ejemplos reales

- **`InputStreamReader`**: adapta `InputStream` (bytes, Adaptee) a `Reader` (caracteres, Target) usando un charset. `OutputStreamWriter` hace lo inverso.
  ```java
  Reader reader = new InputStreamReader(inputStream, StandardCharsets.UTF_8);
  ```
- **Spring `HandlerAdapter`**: el `DispatcherServlet` (Client) invoca handlers de distinto tipo (`@Controller`, `Controller`, etc. = Adaptees) a través de `HandlerAdapter` (Target), con implementaciones como `RequestMappingHandlerAdapter` (Adapter).

## 12. Patrones relacionados (todos "envuelven", distinta intención)

| Patrón | ¿Cambia la interfaz? | Intención |
|---|---|---|
| **Adapter** | ✅ Sí | Traducir una interfaz incompatible |
| **Decorator** | ❌ No | Agregar comportamiento |
| **Proxy** | ❌ No | Controlar acceso (cache, lazy, seguridad) |
| **Facade** | Nueva, simplificada | Simplificar un **subsistema** entero |
| **Bridge** | — | Separar abstracción de implementación **por diseño** (proactivo) |

Adapter es **reactivo** ("bolted on"): se aplica cuando dos cosas ya existentes no encajan. Bridge es **proactivo** ("designed in").

## 13. Chuleta final

- **Target** = lo que el cliente espera (interfaz).
- **Adaptee** = lo que ya existe y no puedo tocar.
- **Adapter** = `implements Target` + tiene un `Adaptee` inyectado + traduce.
- **Client** = solo conoce `Target`.
- Preferí **Object Adapter** (composición) sobre Class Adapter (herencia).
